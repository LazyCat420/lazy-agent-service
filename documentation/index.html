Durable model completions for Obsidian Vault Notes

PUT /obsidian-completions/:id accepts a client-generated UUID, a permitted model endpoint and the OpenAI completion payload. GET /obsidian-completions/:id fetches status and the saved response. Requests follow the service's existing project/username tracking middleware; the UUID is also required to retrieve the job. These headers are application scoping, not a new authentication mechanism.

GET /obsidian-completions reports {version: 1, durableVaultChat: true}. The plugin checks this contract with a bounded timeout before routing a new message to durable storage. Older and unreachable servers retain the original direct model transport, preventing a missing backend deployment from blocking ordinary chat.

The endpoint permits only the existing Jetson and Gold Spark text servers and limits concurrent jobs to eight. It writes an acceptance record before returning HTTP 202 and starts one bounded, non-streaming model request. Disconnecting the initiating HTTP client does not cancel inference. The identical UUID and payload return the existing job, while a changed payload with that UUID is rejected.

Jobs are scoped by project/username and stored in obsidian-completions/ beside the configured runtime store. On the NAS this is inside the mounted runtime-data directory. Completion and failure outcomes are saved using a temporary file and rename. If the process restarts during a running job, retrieval records a failure explaining the interruption; it does not replay the model request. Results currently remain on disk until explicitly removed by the operator.

The plugin owns the agent loop and vault tools. A model step finishes on this service while Obsidian is closed; subsequent vault operations continue when Obsidian reopens. No Prism repository changes are required.

Validation covers persisted acceptance before transport completion, duplicate PUTs with a single model call, durable result retrieval from a second store, scope isolation, mismatched request rejection, endpoint/ID validation and interrupted jobs without replay. The runtime TypeScript build must pass. Deploy from deploy-kit using the existing lazy-tool-service registry ID and verify /health and an accepted/completed model job after restart.

On 2026-10-06 the full suite passed 912 tests and deployment of main@962a506 completed, including image transfer, restart and the HTTP health gate. The trading preflight reported an idle pipeline. The NAS container became healthy, the capability endpoint returned HTTP 200 and /app/runtime-data was confirmed as a persistent mount.

On 2026-10-14 the server-side model-call hard timeout was raised from 180 s to 600 s (override with OBSIDIAN_COMPLETION_TIMEOUT_MS). It must exceed the plugin's per-job poll window maxJobPollMs (default 600 s), which was split from the whole-agent maxAgentDurationMs budget in LLMSortObsidian the same day: a single slow generation no longer pauses vault chat after 3 minutes, and the pause message now distinguishes abort (with reason), plugin unload, and per-job timeout (including the job URL).

A live integration check from LLMSortObsidian used the production chat handler, agent loop and task manager with a simulated empty vault and real HTTP requests. Both model race jobs were accepted on the NAS, the client closed, and a new task manager fetched the saved reply into the original inactive conversation exactly once. Another reload produced no duplicate. That check passed in 4,444 ms. Evidence is in LLMSortObsidian/documentation/artifacts/vault-chat-durable-live-audit.json; it does not claim interaction with the real Windows Obsidian window.

08 — Shared Web Extract & Search Fallback

Date: 2026-10-09. Companion to 04-shared-web-search.md (Exa-only era).

What changed

  1. WebExtractService (src/services/WebExtractService.ts, new): scrape_url on this gateway no longer forwards to tools-service. It reads through scraper-service (POST /scrape, engine: "auto" — http first, Chromium for JS-heavy pages) at SCRAPER_SERVICE_URL (default http://localhost:8001, same convention as treesearch's scraper_client), under a deterministic character budget — no LLM summarization:
    • ≤ WEB_EXTRACT_CHAR_LIMIT (default 15 000, clamp 2 000–500 000, per-call char_limit): whole text.
    • over: head+tail window (75 %/25 %, cut on line boundaries) + [TRUNCATED] footer naming the file holding the FULL clean text ($WEB_EXTRACT_STORE_DIR or /tmp/lazy-agent-web-extract/), so the agent pages the omitted middle with read_file. Stored text capped at 2 MB.
    • Cache: URL + bucketed char limit (2 k/5 k/15 k/50 k/500 k), 20 min TTL, in-flight coalescing; only successes cached; 120 s timeout.
  2. Search fallback (WebSearchService): a failed Exa call (error, rate_limited) now falls back to scraper-service's self-hosted SearXNG collector (POST /collect, source: "searxng"), which answers from the LAN and does not share Exa's rate limits. busy (local queue full) does NOT trigger the fallback — a burst must not pile onto it. Exa stays the primary and the only engine for successful searches.
  3. Compact search rows: search_web snippets are capped at 240 chars in the orchestrator reply (omp's formatForLLM cap), so ten results cost a fraction of the context one long snippet would.
  4. Tool guidance: scrape_url's schema description now teaches the search → extract loop ("use AFTER search_web, pick 2–3 promising URLs, read the stored file when truncated, prefer narrower queries over scraping many pages"). DeepResearchPersona gains scrape_url in its tool set and matching identity text. search_web's description still lives in tools-service (not editable here).

Chapter 12 — Wallgarden Jetson (nemotron35) Priority Gate & Candidate Classification Cutoff (2026-10-20)

Context & Root Cause

The youtube-wallgarden Discovery Feed calls lazy-agent-service (/api/wallgarden/*), which routes local LLM requests to the Jetson vLLM instance (http://10.0.0.30:8000/v1, serving nemotron35 / nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4 with max_num_seqs = 2).

Audit findings on 2026-10-20:

  1. EXPECTED_JETSON_MODEL in src/services/wallgarden/WallgardenService.ts was still hardcoded to "cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit", causing a false warning on every request before runtime fallback selected nemotron35.
  2. Unbounded concurrent browser requests—dominated by POST /wallgarden/classify-candidates firing on every feed batch—queued up to 24 requests on the 2-slot Jetson vLLM (ttg 60–77s), causing browser timeouts (AbortError after 12s) and starving high-value topic generation (extract-topics, brainstorm, similar).

Changes (320bd24)

  1. Pinned EXPECTED_JETSON_MODEL = "nemotron35" in src/services/wallgarden/WallgardenService.ts.
  2. In-Process 2-Slot Priority Semaphore (runWithJetsonGate):
    • Caps concurrent Jetson LLM calls from Wallgarden at MAX_IN_FLIGHT = 2.
    • Enforces strict priority ordering (FIFO within each tier):
      • Priority 0 (Interactive / Creative Generation): brainstorm, similar, extract-topics
      • Priority 1 (Curation): judge-topics
      • Priority 2 (Background): taste-profile, recommend-channels
    • Rejects queued requests with priority >= 1 after 90,000ms with JetsonGateQueueTimeoutError (HTTP 503) so background traffic fails fast instead of saturating the Jetson queue.
    • Exposes live gate telemetry (maxInFlight, inFlight, queued, rejected) on GET /api/wallgarden/models.
  3. Disabled POST /api/wallgarden/classify-candidates:
    • Route in src/routes/WallgardenRoutes.ts immediately returns HTTP 200 with { classifications: [], disabled: true } and zero LLM calls. Candidate filtering is handled deterministically by the client-side rules and the NAS brain_graph.py grounding scorer.
  4. Verified /no_think on nemotron35:
    • Live probe against http://10.0.0.30:8000/v1/chat/completions confirmed reasoning_content: null and completion_tokens: 5, so no extra template flags were required.

Verification

  • Unit tests in src/services/wallgarden/__tests__/WallgardenJetsonGate.test.ts and src/services/wallgarden/__tests__/WallgardenService.test.ts (61/61 tests passing via testrun).
  • Deployed to Synology NAS (10.0.0.16:5591) and verified GET /api/wallgarden/models.

First-Party Chat UI + Disconnect-Safe Persistence (2026-10-10)

Mode: Implement. Repo: lazy-agent-service. prism-client untouched.

Problem

When a user left the chat tab and returned, messages failed to send. Root causes (all evidence-backed, see diagnosis transcript history://GLM-ChatTabResumeDiag):

  1. Client: pendingRun cleared only on terminal events — a dropped connection set canSend=false forever; sends silently returned ''.
  2. Server: POST /chat SSE aborted generation on client disconnect (persistOnDisconnect=false), unlike /agent.
  3. No replay for chat; user+assistant messages persisted only at finalize, and the abort-throw path persisted nothing.

Changes

Server — src/routes/ChatRoutes.ts

  • /chat SSE passes persistOnDisconnect: true (mirrors AgentRoutes.ts), so a dropped connection no longer truncates generation.
  • handleStreamingText records partialAssistantText before rethrowing; the handleConversation catch path persists user + partial assistant message via appendAndFinalize — never skipped on signal.aborted.
  • Test: src/routes/__tests__/ChatSsePersistOnDisconnect.test.ts (red→green; 203 touched-area tests pass).

Package — packages/agent-chat@0.3.0

  • src/turnTransport.ts: buildTurnPayload, ingestTurnEvent, ingestStreamClosed — maps the prism turn-stream wire taxonomy onto the reducer; unknown events counted in state.unrecognizedEvents. Fixtures in test/fixtures/turn-events/.
  • src/presentation.ts: activityFeed (chronological thinking/tool/worker/status rows with durations), THINKING_DOTS_CSS/THINKING_DOTS_CLASS, renderActivityIndicator.
  • Tests: 34/34 package-wide.

UI — served at GET /chat (public/chat/, esbuild bundle)

  • Transcript, composer, send/stop, agent/model/thinking toggles, conversation continuity (?conversation= + lazychat:conversation localStorage), identity headers (x-project, x-workspace-root, x-username, x-profile-id).
  • Animated . .. ... thinking indicator + live activity feed rows ("Running tool: X", "Tool X done (1.2s)", worker stages) under the streaming message.
  • Tab-switch recovery: SSE drop → ingestStreamClosed → retry banner → refetch GET /conversations/:id → mergeConversationSnapshot reconcile → queued sends drained.
  • Tests: test/chat-ui/reconcile.test.ts (11). Full suite: 1336 tests green.

Verification

  • Smoke (mock SSE server scripts/chat-ui-smoke-server.mjs): happy path shows dots + activity rows + stop button; drop path reconciles after refetch; queue drains. 18 browser tabs closed after.
  • Deploy fixed: esbuild was missing from devDependencies (container pnpm run build exit 127) — added in commit 5609fea.

Non-goals

Symptom

In html-notes, news and general questions (tested with nemotron35) came back with no summary at all. /execute/web_search returned 0 results.

Root cause

  1. Exa's keyless MCP reports its free-tier rate limit as HTTP 200 with _meta["ai.exa/rateLimited"]: true and the text "You've hit Exa's free MCP rate limit". WebSearchService.callExa read that as a successful search with 0 results.

  • Any Exa reply without results falls back to SearXNG through scraper-service /collect.
  • Only an ok reply with at least 1 result is cached.
  • SCRAPER_SERVICE_URL defaults to http://10.0.0.16:8001.

Obsidian harness admission and recovery

The Obsidian client persists an idempotency key, accepted run ID, replay cursor, and each local tool observation before acknowledging it. A delivery interruption resumes the same run through the existing scoped event replay API. A started mutation without a saved observation pauses for inspection. Transport failures never restart the goal through another agent path.

Runtime changes

  • POST /v1/runs/:runId/tools/:callId/verify verifies the persisted signed receipt and every scope/argument field before the client performs a local effect. The route enforces existing vault, profile, project and user scope. Signing material remains on the backend.
  • runtime_overrides.detached_delivery=true keeps execution alive when an SSE client disconnects. Explicit cancellation and server duration/tool/token budgets still apply. Other clients retain disconnect cancellation by default.
  • Receipt-bound tool errors are persisted and returned as model-visible errors for repair, with tool.failed telemetry. Policy rejection and invalid admission still fail closed.
  • POST /obsidian-completions/:id/cancel aborts only the matching scoped durable model job. The terminal cancellation response is persisted, so fetching the same request ID cannot restart it.
  • The Obsidian profile admits outlines, section reads/patches and undo. It supports the served GLM-5.3-Flash-EXL3-TF model while retaining the older alias. Obsidian application context is user data; it cannot grant new tools or change system policy.

Compatibility and limits

The profile version remains 1.0.0 because the additional tools are additive. Deploy the service before the plugin: an older backend lacks pre-effect verification and the upgraded client will pause safely. An application reload preserves delivery but a service restart can invalidate a pending local waiter; this remains an explicit stopped outcome, not a replay of an uncertain write. Replaying a saved result acknowledges it without executing it again.

Verification does not make arbitrary filesystem effects transactional. The plugin uses exact paths, revision checks, Obsidian's atomic process callback, persisted undo records and final artifact checks. User intent and content quality are graded separately in the LLMSortObsidian outcome benchmark.

Shared harness embeddings and EmbeddingGemma 2 audit

Embedding generation already belonged to lazy-agent-service before this change. It is not a trading-only feature. Embeddings represent text for retrieval and clustering; they do not replace generation models or run on every reasoning/tool step.

Shared integration

The default text embedding provider is now jetson-embedding, using embeddinggemma-2 at http://10.0.0.30:8001/v1. The client verifies google/embeddinggemma-2, revision 914f7f89142e33e77833254d9c9b90c3cef7303b, 768 native dimensions, readiness and quarantine state. HARNESS_EMBEDDING_URL can override the endpoint. No API key is required. Existing EmbeddingGemma settings and instance aliases resolve through the shared client. Explicit cloud provider/model selections remain supported, and configured models take precedence over provider defaults.

Any repository can use POST /embed on lazy-agent-service (NAS port 5591). Provider/model fields are optional. Supply the repository's x-project header and the caller's x-username header for attribution:

{"text":"Find the deployment recovery procedure","input_type":"query","dimensions":768}

Use input_type: "document" for indexing and "similarity" for symmetric comparisons. The existing taskType values RETRIEVAL_QUERY, RETRIEVAL_DOCUMENT and SEMANTIC_SIMILARITY work too. Unspecified tasks default to document retrieval. Send plain text; the server owns task prefixes. Responses include embedding, dimensions, provider, model and space.

To index a corpus, send texts (1–32 strings) instead of text. The response carries embeddings in input order, plus the same dimensions, provider, model and space as a single request. A batch is logged as one request row with counts only, never the texts. The whole batch holds the shared Jetson queue, so keep batches small (trading sends 8). Run corpus jobs through this endpoint rather than against the Jetson directly: a separate process has its own queue. While one ran on 2026-10-06, every live /embed call failed with HTTP 429 after its three retries.

Off-the-shelf clients use the OpenAI shape instead: POST /v1/embeddings with base URL http://10.0.0.16:5591/v1 (OpenAI SDKs, Oh My Pi, LangChain). It accepts input as a string or up to 32 strings, model (embeddinggemma-2, google/embeddinggemma-2 or embeddinggemma), encoding_format (float or base64) and dimensions. It answers {object:"list", data:[{object:"embedding", index, embedding}], model, usage} plus space. Without input_type it uses the symmetric similarity task: a generic client sends queries and documents through the same call, and only a symmetric representation is comparable between the two. Clients that can tell them apart pass input_type (OpenAI SDKs: extra_body). Same model, queue and spaces as /embed.

The Jetson adapter is text-only. The existing cloud embedding providers retain their own modality capabilities. Long text is split at Unicode character boundaries into at most 1,800 UTF-8 bytes per chunk. Requests pack at most eight chunks within 7,000 total UTF-8 bytes; chunk vectors are summed and L2 normalized into one document vector. This is a bounded representation of the full text, not token-exact splitting or silent truncation. Token-limit refusals are surfaced. Index identity records the chunking/aggregation policy, model revision and dimensions. Use the same client and policy for query/document representations.

Calls are serialized within each service process, with a 60-second inference timeout. HTTP 429 observes numeric Retry-After with at most three attempts and a ten-second maximum delay. HTTP 503/quarantine and other refusals are surfaced immediately. Other callers on the LAN can still contend with this process; the Jetson's own single-inference guard remains authoritative.

Shared keyless web search

POST /execute/web_search searches the web through Exa's free keyless endpoint, with one cache and one rate limit for every service on the network. It replaces each project scraping DuckDuckGo on its own. Implemented in src/services/WebSearchService.ts and routed in LocalToolRouter, next to news_search.

Why

Every machine in the house leaves through one public IP, 71.198.70.27; the NAS and the workstation both report it. The free search engines bot-block that IP:

  • DuckDuckGo first refused the NAS on 2026-07-27.
  • On 2026-10-06 a plain curl from the workstation got DuckDuckGo's "bots use DuckDuckGo too" challenge, and Startpage, Ecosia, Google and Mojeek failed in the same way.

A read-only audit on 2026-10-06 found 17 DuckDuckGo code paths across the workspace. The largest automated ones:

  • html-notes' health check searched about 288 times a day; fixed on 2026-10-06 (html-notes docs/WEB_SEARCH.md).
  • treesearch-service searches on every boot.
  • trading-client's chat turns web search on for news-like messages.
  • Rod's tools-service search_web is DuckDuckGo only.

Several used the ddgs library, which on a blocked IP tries about nine engines for every call.

How it works

Exa answers from its own index through an API. It does not scrape anyone's result pages, so the bot checks that block this IP do not apply. The free tier answers HTTP 429 when called too fast, so this service is the one place that calls it:

  • Cache: identical searches are answered from memory for 30 minutes, ignoring case and spacing. Identical searches already in flight share one call.
  • Pacing: Exa calls go out one at a time, at least 1.5 s apart, for the whole network. A caller whose turn would come more than 20 s later gets busy instead of waiting.
  • Rate limits: after a 429, or a JSON-RPC error that says "rate limit", nothing is sent for 60 s, and callers get rate_limited immediately.
  • No scraping fallback, on purpose. News lookups have their own tool, news_search, which uses keyed news APIs.

The rolling window (context management), side by side

Prism, per loop iteration:

  1. Knows the real context window: the model's maxInputTokens, else vLLM's max_model_len read from /v1/models (utils/ContextLengthDiscovery.ts), else 128k.
  2. Estimates the next request from the provider's last reported input plus the growth since, calibrated against real usage (compact/ContextBudgets.ts), counting messages, system prompt and tool schemas.
  3. Derives both thresholds from one budget so it always summarizes before it truncates.
  4. Protects the last 4 model calls (not user turns: a long agent run has one user turn) up to 20k tool-output tokens (compact/RecencyProtection.ts).
  5. Shrinks in order: defer while results are unread; move old large tool results losslessly to Mongo behind an offload_id (ToolResultOffloadService, readable with retrieve_offloaded_content); LLM-summarize everything older than the recency window, judge the summary, persist the boundary; as a last resort cap old results, compress old turns, slide the window — never touching the protected calls. Originals are kept verbatim (TurnTranscript, MessageLineage).
  6. Clamps the output budget to what is left (ContextBudgetTracker), refuses a call that cannot get 4,096 output tokens (ContextExhaustionGuard, runs a summary pass instead), and halves maxTokens and retries on a context overflow rejection.
  7. Bounds every tool result at 8,000 characters / 10 list items behind a preview.

Ours today (verified for points 1 and 2):

  1. Protection counts user turns. A trading run sends one or two user messages, so the protected range starts at the first message and nothing is ever shrunk; enforce() reports "truncated" and returns the input unchanged.
  2. No context window for vLLM models: getModelByName reads a static catalog with no vLLM entries, so the output clamp returns early, the 4,096 guard never fires, and every threshold assumes 128k. No discovery, no overflow retry.
  3. The estimate counts messages only (no system prompt, no tool schemas, fixed 256-token margin, no calibration).
  4. LLM compaction runs only if Settings→Memory names an extraction model; its breaker is process-wide; on a single-turn run a summary can make the prompt bigger.
  5. Results: trading results are cut at 50,000 characters, objects are sliced mid-JSON at 8,000, strings pass whole. No offload store, ledger or deferral.

What a long trading run would see on ours: every result stays verbatim on every request, the prompt grows linearly until prompt + maxTokens passes the box's max_model_len, vLLM answers 400, and the turn ends with an error and no artifact. A stalled stream hangs until trading's 1,800 s agent timeout (no body timeout or idle watchdog on our provider client).

1. Verdict: REQUEST CHANGES

The task-level schedule is faithful. The details are listed in §5 so nobody "fixes" them:

  • the 4k-rollout / 3k-stage budget, the INV/DOM split, one retry then fallback, KEEP_BASE;
  • sequential checkpoints, and the parallel compose.

The decision points around the schedule are not faithful. These are what gets selected, what gets stored, what evidence the improver sees, and what a skill costs. Three of them corrupt what the loop learns:

  1. Failed runs still write library lessons (R4, R5). Fixed in 94883af.
  2. Empty or cut-off improver replies are recorded as deliberate "keep the base" decisions (R2, R3). Fixed in a3993ea.
  3. A re-run task reads its own earlier answer (R6). Fixed in a3993ea.

The loop is also not closed. Nothing outside /harness2 reads the library or an adopted harness (§4.B4), so no production agent improves from it. The rollouts don't run a real agent either (§4.B1). With no agent persona, a tools-on rollout is offered about 50 tools, all auto-approved, though harness2 asks only for calculate_precise.

Does the loop improve the solver? Measured in §10, on fresh attempts.

  • Within a task, yes, when it starts from a reasonable harness.
    • From a neutral base harness, the harness the loop adopts beats the base by +0.25 per task (95% CI [+0.03, +0.48], 10 tasks).
    • That is about half of what a hand-written harness gains over the same base: +0.475 [+0.33, +0.65]. That gain was measured in a separate run, so "half" is approximate.
  • From a deliberately weak base it gains much less: +0.15 [+0.03, +0.30], against +0.65 for the hand-written harness in the same run. Each candidate is judged on a single in-loop attempt, and when every attempt fails the loop keeps the base.
  • Across tasks, no measurable effect. The library of lessons changed nothing measurable: +0.00 [−0.17, +0.22] from the weak base, and +0.00 [−0.31, +0.25] from the neutral base. Its lessons are mostly cautions about evidence, not knowledge about the task.
  • Caution: the same harness scored +0.225 higher in one run than in another, so only comparisons made within one run are sound (§10).

Exposure was small: at audit time the route was live on the NAS, but no library existed there yet (§2), so nothing relied on stored lessons. The fixed route has run on the NAS since 2026-10-22 23:26 UTC (§9, "NAS deploy").

4. Findings

A. The loop's decision points

A1 — The selection pool includes the base runs, and k=1 still runs a selector. CONFIRMED (R17).

  • Ours: selectOutput builds the pool from the base rollouts plus the finals (Harness2Service.ts:111). Its comment calls this the upstream "mixed" pool.
  • Upstream: selection_pool is "exactly the k finals… the reference executions are not in the pool… the only pool this release builds" (selection.py:93). run_task refuses any other policy. At k=1, upstream delivers the single final with no selector call (trivial_selection, schedule.py:514).
  • Effect: our method is not the one the paper measured. Every k=1 run spends an extra improver call, and a base output can be "adopted", which then stores the base tree as a lesson. The mixed pool does have a real argument (it lets an unadapted answer win when adaptation hurt). That makes this a decision for the user (§6 Q1), not a silent default.
  • Status: default changed to upstream's in 94883af; Q1 is still open for the user.
    • The pool is now the k finals. At k=1 the single final is delivered with no selector call (selection.trivial).
    • selectionPool: "mixed" keeps the old pool as an opt-in.
    • Consequence at k=1: if agg1 delivers nothing, the run returns status no-output and no output, even when base1 delivered. Every rollout's output stays in result.rollouts.

A2 — The "blind, shuffled" order is the same for every task. CONFIRMED (R1).

  • Ours: the seed defaults to 0 (Harness2Service.ts:188), so a 2-candidate pool always comes out [agg1, base1]. Upstream seeds per task: sha1(task|k|mode) (selection.py:71).
  • Effect: in the repro, a selector that always answers a1 picked agg1 on 12 of 12 different tasks. LLM selectors do lean toward one position, so this turns position bias into a systematic pro-adaptation bias.
  • Status: fixed in 94883af. selectionSeed hashes task|k|mode (plus the caller's seed when given) and shuffles a canonical sort, as upstream's assign_ids does.

A3 — Failed selections still write library lessons. CONFIRMED (R4, R5).

  • Ours: reflection and library.add run unconditionally (Harness2Service.ts:193-207).
    • If nothing delivered, selectOutput returns base1 with an error, and an entry is still stored (R4).
    • If the selector fails, the first shuffled candidate is "adopted" and stored (R5).
  • Upstream: reflection runs only if mode_lib and sel.ok, and the library add requires sel.ok plus a complete experience (schedule.py:529, :555). A fallback pick delivers an output but never teaches.
  • Status: fixed in 94883af.
    • Reflection and library.add run only when the status is ok and the chosen run delivered.
    • A selector failure delivers upstream's neutral fallback and sets selection.fallback, with status selection-fallback. Nothing is learned from it.
    • selection.ok is false and chosenLabel is "" when nothing delivered.

A4 — No stop when every base rollout failed. CONFIRMED (R12).

  • Ours: with the solver down, the run still made 4 improver calls (inv1, dom1, agg1, experience) and 4 doomed rollouts.
  • Upstream: stops with status base-failed (schedule.py:629). It also refuses to build evidence when no trajectory renders ("the proposer would be adapting on nothing").
  • Status: fixed in 94883af. With no base rollout ok, the run returns base-failed after zero improver calls, and errors[0] carries each base error.

A5 — An empty or cut-off improver reply looks like a deliberate KEEP_BASE. CONFIRMED (R2, R3).

  • Empty reply: makeProposer returns res.text || "" (Harness2Service.ts:166). applyReply then keeps the current tree, so the stage records keptBase=true, fellBack=false with empty notes (R2). Downstream stages and the reflector read that as an evidence-based "no change".
  • Cut-off reply: a reply truncated inside a second <file> block is half-applied, and it passes validation. In R3 the accepted tree tells the agent to "use the totals skill", but that skill does not exist.
  • Nothing checks finish_reason or zero usage. Compare memory zero-reported-token-usage-marks-a-truncated-generation.
  • Status: fixed in a3993ea.
    • makeProposer throws a ProposerError on empty text or all-zero usage. An empty string from any proposer is a failed transport attempt.
    • After 2 attempts the stage falls back with proposer failed: empty reply (after 2 transport attempts), never keptBase.
    • A reply that leaves a <file> block open is rejected with "cut off inside the <file> block" and retried.
    • generateText exposes no finish_reason, so a cap hit that still closes every block is accepted. A cut-off selector or reflector reply fails its own parse and falls back.

A6 — Stage retries are weaker than upstream's. CONFIRMED (R13, R21, R8).

  • No transport retry: a single ECONNRESET ends the stage on the first attempt (Recursion.ts:170-173). Upstream makes 2 transport attempts with backoff (config.py:177, proposer.py).
  • The retry is blind: it appends "YOUR PREVIOUS ATTEMPT WAS REJECTED… Fix it", but the proposer call is stateless and never sees what it sent (R21). Upstream writes the rejected tree back into the session's workspace, so the retry edits it (recursion.py:228).
  • First error only: validateTree throws at the first problem. A reply with 4 problems reported only one (R8). Upstream collects every error into one message (tree.py:377).
  • No autotrigger: upstream repairs a missing skill trigger line before validating (recursion.py:116, tree.py:192). That is the exact failure the 10-19 smoke run hit (a DOM proposal retried, then fell back).
  • Status: fixed in a3993ea.
    • Transport: 2 attempts with backoff of 10 s × (attempt − 1). A deadline is not retried, because generateText takes no abort signal and the timed-out call keeps generating.
    • Retry: it edits the rejected tree, and its prompt shows that tree and the rejected notes.
    • Validation: collectTreeErrors reports every problem in one message.
    • autotrigger: appends `- When <description>, use the <name> skill. to guardrails.md, unless that would break the cap (stage.repaired` lists the skills it fixed).

A7 — Library scoping and retention. CONFIRMED (R6, R9) and code.

  • Self-read: a re-run task reads its own earlier entry as "earlier tasks in this domain" (R6). Upstream keeps only the entries before the current task (library.py:101, schedule.py:701).
  • Eviction is alphabetical: past the 60,000-char cap, contextText drops "the oldest", but entries() sorts by name (Library.ts:142). R9 added zeta-older and then alpha-newer; the newer one was evicted.
  • One library forever: there is one library per domain, shared across mode, k, solver and improver, and it grows without end. Upstream scopes roots per run and mode, "so each sweep starts every domain empty" (library.py:23).
  • No way to remove a bad lesson: there is no forget/retain and no delete endpoint.
  • Caller-chosen task ids overwrite: a reused taskId replaces an unrelated earlier entry.
  • Status:
    • Fixed in a3993ea:
      • Self-read: contextText({ exclude: [taskId] }) drops the task's own block and its index row.
      • Eviction: each entry gets a - stored: time; entriesByAge evicts the oldest first, and the context says how many entries it left out.
      • Library.forget() exists.
    • Fixed in 2ad3f48: DELETE /harness2/library/:domain/:taskId.
    • Open: library scope (Q5).
    • Unchanged: a reused taskId still overwrites its entry, as upstream's add does.

A8 — The reflector cannot read the selector's reasoning, and its prompt lost the anti-confabulation rules. CONFIRMED (R18) and prompt diff.

  • No id map: the selector writes its <why> in anonymous ids ("a2 reconciles the total"). The reflection prompt carries that text but not the a1/a2 → label map. Upstream writes adoption.json for exactly this (selection.py:432, :471).
  • Base tree twice: the base tree is rendered as CURRENT HARNESS and again as BASE HARNESS.
  • Dropped sentences: experience() (Prompts.ts:264) dropped upstream's strongest lines, including "an invented attribution poisons the library for every later task" (prompts.py:1130) and "Adoption alone never establishes that an edit helped or will transfer" (prompts.py:1145).
  • HYPOTHESIS: the 10-19 smoke run's "high confidence lessons from sampling noise" is partly caused by these cuts, not only by the weak improver model. Testable: A/B the two prompt texts on the same recorded evidence.
  • Status: fixed in a3993ea. The reflection mission is now:
    • the BASE HARNESS, shown once;
    • every candidate, diffed against the base;
    • an ADOPTION block: the submitted label, how it was selected, the a<n> → label map, and the selector's reason.
    • experience() restores the dropped lines. The hypothesis is still untested.

A9 — Evidence is clipped below upstream's floor, and the prompt grows without bound. CONFIRMED (R19, R20) and code.

  • What the improver sees: each tool result is cut at 800 chars, args at 400, thinking at 1,500 and the final output at 6,000 (Harness2Service.ts:135-140). Selector candidates are cut at 12,000 (:121).
  • Upstream's floor: an observation limit under 10,000 is "in the range that fabricates defects" and is refused (spec.py:163). Trajectories are never clipped as a whole, and the model is told that truncation markers "are ours, not behavior by the solver" (context.py:534). Our selector has a FINISH rule against "visibly incomplete sections" and gets no such disclaimer (R19). Upstream's has one (prompts.py:1087). This biases selection against long answers.
  • Size: everything is inlined, and there is no cap on tool-call count or total mission size. At k=4, with 20 tool calls per rollout, the aggregator prompt was 394,106 chars (about 98k tokens) before any library text (R20).
  • ASSUMPTION: whether that overflows GLM-5.3-Flash depends on the served context length, which this audit did not check. An overflow surfaces as "proposer failed", which means a silent fallback. (Later check: the deployed vllm-2 no longer serves GLM at all; see A14. The Jetson's nemotron35 serves max_model_len=100000 tokens.)
  • Status: the selector's truncation-marker sentence is fixed in 94883af (R19). The rest is fixed in a3993ea:
    • Caps: thinking 4,000, tool args 2,000, tool results 10,000 (upstream's floor), final output 20,000.
    • Truncation note: every mission states that truncation markers are ours.
    • Budget: past a 240,000-char mission budget (HARNESS2_MISSION_CHAR_BUDGET), trajectories are compacted. Each keeps its start and end, behind an explicit COMPACTED note. R20 now builds a 239,332-char prompt.
    • Selector: each candidate gets min(40,000, budget / n).

A10 — The cost of skills is misrepresented, and nothing caps always-on text. CONFIRMED (R14, R15).

  • What we do: materialize puts every skill body into every rollout's system prompt (HarnessTree.ts:98-108). In R14, a 53-char system prompt plus a 5,048-char skill gave a 5,173-char system prompt.
  • What we tell the proposer: the surface table says skills are "used only when its trigger fires" (Prompts.ts:49). It also says "ALWAYS-ON PROSE IS THE EXPENSIVE OPTION; prefer a SKILL" (:51).
  • Effect: on this substrate that advice is false. The proposer is steered to grow the prompt and cannot see the cost.
  • No cap: a 200,000-char systemprompt.md validates (R15). Upstream caps always-on text at 24,000 chars (OpenCode, substrate/opencode.py:50) or 8,000 (Codex, codex.py:42).
  • We already have on-demand skills: SkillRegistry plus the skill_read tool, using the same skills/<name>/SKILL.md layout (AgenticLoopService.ts:361-378). See §6 Q2 and D5.
  • Status: Q2 default applied in a3993ea; Q2 itself is still open for the user.
    • Skills stay inlined.
    • The surface table now says skills are always on here and cost the same as always-on prose.
    • ALWAYS_ON_MAX caps the materialized prompt at 24,000 chars, skill bodies included.

B. How rollouts run through our agentic harness

B1 — Rollouts do not exercise the real agent. CONFIRMED (code).

  • The executor: runSingleModel (BenchmarkService.ts:323). Without toolsEnabled there are no tools at all. With it, it calls handleAgent with autoApprove: true, maxIterations: 10 and enabledTools: [CALCULATE_PRECISE] (:383-392).
  • What the solver can call (corrected 2026-10-22): harness2 asks for calculate_precise (evaluate_expression) only, but the solver is offered far more.
    • A rollout runs with no agent persona, so coreToolsLocked defaults to true (AgenticToolResolver.ts:274).
    • The resolver then also passes (:313-333):
      • every core-domain tool from tools-service (read_url among them);
      • the orchestrator tools (create_subagent, send_subagent_message, …);
      • execute_python and emit_structured_output;
      • think, unless the model thinks natively (:393-395).
    • The agentic loop adds its internal tools: take_note, ask_user and retrieve_offloaded_content always, plus skill_read when repo skills exist (AgenticLoopService.ts:361-378).
    • Measured by the §10 benchmark: every rollout was offered the same 47 tools by the resolver, then the loop's own tools on top, so about 50.
      • Arithmetic: evaluate_expression.
      • Code and shell: execute_python, execute_javascript, execute_command, kill_process.
      • Files: read_file, write_file, delete_file, move_file, apply_patch, replace_in_file, edit_notebook, run_git, commit_split.
      • Datastore and schedules: write_datastore, delete_datastore, create_cron_job, trigger_cron_job, delete_cron_job.
      • Agents and tasks: create_subagent, send_subagent_message, stop_subagent, delete_subagents, create_task, update_task.
      • Web: read_url, search_web.
      • The rest are lookups (listing, searching and reading), plus debug, think, sleep, save_memory and emit_structured_output.
    • All of them are auto-approved.
      • decideToolCall allows any tool that is not read-only once autoApprove is set, unless a DENY policy binds (ToolAuthorization.ts:201-219).
      • A rollout passes no policies.
    • So a harness the improver wrote can steer the solver, with no person in the loop, into:
      • running commands;
      • writing or deleting files in tools-service's workspace on the NAS;
      • creating cron jobs or spawning sub-agents.
    • This opens no new door:
      • the service enforces no auth (AuthMiddleware only reads identity headers);
      • /agent already accepts autoApprove from any caller.
    • What is new: harness2 does this unattended, following prompts that a model wrote. The proposed restriction is Q6 in §6.
    • A local run without TOOLS_SERVICE_URL gets no tools-service tools, calculate_precise included. The first reading of this finding ("the only domain tool") held only for that case.
  • No real agent: makeExecutor never passes model.agent (Harness2Service.ts:144-155), so a rollout cannot run as a real custom agent (trading, lupos, …) with its own tools and policies.
  • Effect: tool_guidance.md and the INV dimension have no real tool use to adapt. Harnesses learned here are not evidence about production agents.
  • ask_user can stall a rollout and the whole run:
    • ask_user parks the turn until someone answers over POST /agent/answer, or until the turn's abort signal fires (harnesses/lifecycle/AskUserTool.ts:142-185). It also stores a pending question first.
    • harness2 passes no signal, and the loop then substitutes one that never aborts (AgenticLoopService.ts:557).
    • Neither the loop nor ChatRoutes.ts has an overall timeout.
    • Result: a tools-enabled rollout whose model asks a question waits indefinitely, and so does the synchronous POST /harness2/run. A proposer writing "ask the user when unsure" into guardrails.md would trigger exactly this.
    • Status: fixed in 2ad3f48. Every rollout now ends:
      • it gets its own AbortSignal with a deadline (HARNESS2_ROLLOUT_TIMEOUT_MS, default 20 min) and follows the run's cancellation;
      • its first ask_user call aborts it, recorded as "no user is attached";
      • if it ignores its abort, it is abandoned after 30 s.
      • The ask_user schema is still offered to the solver. Removing it means changing AgenticLoopService.ts, which two other worktrees are editing.
  • Side note: take_note writes data/notes/<runId>.md. That path is not on a container volume and is not gitignored in a checkout.

C. Route and operational safety

C1 — An open, expensive endpoint. CONFIRMED (code).

  • No authentication: authMiddleware only copies the project and username headers (AuthMiddleware.ts:12-58). This is service-wide, so Rod's repos can call without keys.
  • Cost: at k=4, one POST /harness2/run can start 16 rollouts and up to 24 improver calls (12 stages × 2 attempts), plus selection and reflection.
  • Load on the Spark: the default improver is GLM on the DGX Spark (vllm-2), the same box that serves the trading cycle. Nothing queues or prioritises these calls, and nothing stops two runs at once.
  • Any model: the body may name any provider/model as solver or improver, including paid cloud models.
  • Status: partly fixed in 2ad3f48.
    • Solver and improver must be local providers unless HARNESS2_ALLOW_CLOUD=1.
    • A preflight confirms each local model is served before any rollout (A14).
    • Only one run per domain can be active.
    • Unchanged: there is still no authentication (it is service-wide, and Rod's repos call without keys), and the Spark still has no queue or priority.

C2 — A synchronous request with no run record. CONFIRMED (code).

  • Results live only in the HTTP response. The response is returned after the whole run. Nothing aborts on client disconnect, and nothing persists stage notes, selection, raw reflection or proposer prompts.
  • Upstream keeps a full record: summary.json (with resume), selection.json, edits.md, per-stage evidence directories and a proposer audit trail.
  • Effect: when a run dies late (A11), or the client times out, everything except a possible library entry is gone.
  • Status: fixed in 2ad3f48.
    • POST /harness2/run answers 202 with a runId.
    • GET /harness2/runs/:runId polls, and POST /harness2/runs/:runId/cancel aborts.
    • wait: true keeps a synchronous answer, and cancels the run when the client disconnects.
    • Every run writes <libraryRoot>/<domain>/runs/<runId>.json: the request at start, then the whole result or the error. A record still running with no live job reads interrupted.
    • Proposer prompts are not stored, and there is no resume (upstream has both).

C3 — .. escapes the library directory. CONFIRMED (R10; path computation only).

  • slug keeps dots (Library.ts:29). So domain: ".." resolves to the parent of the library root, and taskId: ".." resolves to the domain directory itself. Both GET and POST accept them.
  • Reach is one directory level, because slashes are replaced.
  • Status: fixed.
    • slug replaces leading dots, so .., . and .x stay inside the root (a3993ea).
    • The route refuses any taskId or domain outside [A-Za-z0-9][A-Za-z0-9_.-]{0,127} (2ad3f48).

C4 — Concurrent runs in one domain race. CONFIRMED (code).

  • Two runs in the same domain race on the INDEX.md rebuild. Two runs with the same taskId race on rmSync of its harness directory (Library.ts:88).
  • Status: fixed in 2ad3f48.
    • One active run per domain: a second POST answers 409 with the holder's runId.
    • DELETE of a lesson also waits while the domain runs.
    • The library writes are synchronous, so within one process this guard is the whole fix. Two service processes sharing one library would still need a file lock.

5. What is faithful (keep it)

  • Budget and schedule: 4k rollouts / 3k stages including the k shared base rollouts; INV and DOM per round; parallel = 2k candidates, then k independent compositions; sequential = k rounds editing the previous checkpoint, with KEEP_BASE meaning "keep the current checkpoint".
  • Stage handling: STAGE_ATTEMPTS = 2, with fallback to the stage's current harness. The decisions map carries notes || error.
  • Labelling unchanged candidates: an unchanged candidate is labelled "IDENTICAL… sampling noise" (430d150).
  • Library format: stores the whole adopted tree plus EXPERIENCE.md, and refuses an entry without cue/lesson/evidence. NO_ENTRY means no entry. Domains are isolated.
  • Stage prompts: propose, aggregate and composeRound keep upstream's structure and KEEP_BASE language.

10. Does the loop improve the solver? A benchmark (2026-10-22)

§9 shows that each step of the loop works with real models. It does not show that the loop makes answers better. Its live runs scored the attempts the loop itself chose from, with one attempt per candidate and no comparison against the base harness on fresh attempts. This section measures improvement.

The questions.

  • Within a task: is the harness the loop adopts better than the base harness, on fresh attempts?
  • Across tasks: do lessons from earlier tasks make later tasks' harnesses better than an empty library does?

Design (scripts/harness2-eval/).

  • Tasks: a seeded family of invoice reconciliations (common.ts).
    • Each task has 4–5 distinct invoices, 2 exact repeats and a decoy. The decoy is a line with another line's vendor and amount under a different id, and it counts in the total.
    • Each task ends with two required lines, TOTAL: and DUPLICATES:. An answer is right only if both are exactly right.
  • Solver: vllm / nemotron35 (Jetson), thinking off, tools on.
    • It is offered about 50 tools (§4.B1).
    • The one that matters here is evaluate_expression(operation, a, b) from tools-service: exact arithmetic on two numbers.
  • Improver: vllm-2 / DeepSeek-V4.1-Flash-1017 (Spark), k=1 (the default; finals-only selection).
  • Arms, each scored on 4 fresh attempts per task:
    • base: the base harness, which is also the loop's starting harness. There are two:
      • the weak base (s2), "Be brief: answer in one sentence." It is deliberately weak: one sentence fights a request for a total and a list.
      • the neutral base (s3–s5, --base=neutral), "You are an accounts-payable assistant."
    • handwritten: a hand-written harness, as a reference (never part of the loop). It says to list the kept lines, then add them with evaluate_expression, one add per call.
    • solo-blind: the harness the loop adopts, starting from an empty library, as shipped.
    • solo-told: the same, except the improver also gets one neutral sentence through bench.domainGuidance. The sentence names one of the solver's tools, its signature and what it does, but not what to use it for.
    • chain-blind: the tasks run in order in one domain, so each task reads the lessons of the tasks before it.
  • Decision rule, fixed before any result:
    • An arm improved on another only if the lower bound of the 95% bootstrap interval of the per-task difference is above 0.
    • n is the number of tasks (one loop run each), not the number of attempts.
  • Isolation: as in §9, plus tools-service on the NAS.
    • Mongo is not connected, so workflow memory cannot carry anything from one attempt to the next (§4.B2 hypothesis).
    • The fetch allowlist confines the benchmark process, not the solver. Its tools-service tools (read_url, execute_python, …) run on the NAS.
  • Tripwires: the runner stops (exit 3) if any of these happens:
    • the assembled system prompt changes size by more than 500 characters between solver calls;
    • the solver is offered a different tool set;
    • an attempt hits the context exhaustion guard.

Every attempt also records each tool it called.

  • Raw results: documentation/artifacts/harness2-eval-2026-10-22/.
    • Each of s2–s5 has sN-units.json (every attempt and loop run) and sN-meta.json (the tripwire records: prompt sizes, offered tool sets, trips).
    • report.py output: s2-report.txt, s3-report.txt, s5-report.txt, and s3-s4-library-report.txt for s3 and s4 together.
    • The breakdowns of wrong answers (anatomy.ts): s2-anatomy.txt, s3-anatomy.txt.
    • s3-first-start-tripwire-meta.json: the tripwire record of s3's first start, stopped by §4.B6.

  • Status: the leak is fixed (42e7a48), and s1 is discarded whole. Even its early units ran with inflated tool sections.

Invariants (each one has a stress test in §4c):

  • I1 A run ends completed with non-empty assistant text, unless the client cancelled or the provider is unreachable for the whole run (then failed with the partial text attached).
  • I2 Nothing a tool does (throw, hang, return garbage, return 5 MB) ends the run or the process.
  • I3 Every tool_call_id the model emitted has exactly one tool result before the next model call.
  • I4 The tools array sent to the provider is byte-identical on every call in a run.
  • I5 Budgets are soft first (final answer), hard second (abort at the real deadline). The hard abort never crashes the process (3f3b45e).
  • I6 A tool the run can't execute (local tool with no client) is never offered to the model.
  • I7 Tool results the model sees are capped (default 16 000 chars, head + tail, with a note saying how much was cut).
  • I8 One run's failure never affects another run (concurrent runs isolated; the process stays up).

Deferred mechanisms (design notes)

1. Event-sourced session log with resume

Append every transition (message, tool call, compaction, hook event) to a per-run log (SessionState already exists as the in-memory substrate). Resume = rebuild provider messages from the log tail. Cost: serialization discipline; benefit: crash recovery and time-travel debugging. Start with run-level (not turn-level) resume.

2. LLM-summarizing condenser

Current compaction collapses old tool results into one-line summaries (compactToolResultsForPressure). The Claude Code / Hermes approach summarizes with the model itself at >80% pressure. Requires: a summarization prompt, a budget for summary size, and idempotence (never summarize the summary twice in one run).

3. Formal input/output guardrails + tripwires

SWE-agent style regex/AST tripwires on tool args (e.g. rm -rf, secrets in Write). Plugs into AgentHooks.beforeToolCall — decide/deny already exists; what's missing is the rule library and its config surface.

4. Handoff-with-history (subagent context passing)

DelegateTool currently passes a prompt. Handoff-with-history (Oh My Pi) passes a bounded slice of parent history + notes. Needs NoteStore integration so a delegate reads the parent's run notes.

5. Ranked rule providers / TTSR

RuleLoader loads static rules. TTSR (term salience) ranks rules against the current prompt; only top-N injected. Requires an offline index and a scoring hook in ContextAssembly.

Boot connectAllFromDB also launched every enabled row of prism.mcp_servers, which prism-service shares.One guard in MCPClientService (assertStdioAllowed, called by connect() and again in createTransport) refuses stdio unless command exactly matches MCP_STDIO_COMMANDS (empty by default, so stdio is off) and the row env sets no NODE_OPTIONS/LD_*/DYLD_*. Boot skips and logs refused rows. The routes answer 403 for POST, PUT (judged on the merged row) and connect. transport is now required (400 without it). An allowed child gets only PATH, HOME, LANG, TMPDIR, NODE_* plus the row's env.d1deebd

How it works

Every way a server gets connected goes through MCPClientService.connect(): the /:id/connect route, boot auto-connect, reconnect, authenticate (which writes auth into a stdio row's env) and the OAuth callback. The guard runs there before anything else, including before an existing connection is torn down. createTransport repeats the check right before the StdioClientTransport is built.

A PUT that only sets enabled: false on a refused stdio row is still allowed, so an owner can turn off a row someone else wrote. DELETE is unchanged.

Configuration

MCP_STDIO_COMMANDS (in .env, documented in .env.example): comma-separated absolute paths, exact match. Never list an interpreter or shell (node, npx, python, sh, bash): a row's args stay caller-controlled, so -e would turn it back into code execution. Production had 0 stdio rows when this landed (6 sse, 1 disabled streamable-http).

Tests

src/services/__tests__/McpStdioGuard.test.ts: refused cases use a payload that would write a marker file, so they prove nothing was spawned. They cover POST, PUT, connect, a non-allowlisted command with the allowlist set, and boot skipping a stdio row while still connecting an sse row. The allowlisted case spawns a real stdio MCP server (fixtures/stdio-env-mcp-server.mjs) that reports its env keys; the test checks that no MONGO_*, DATABASE_URL or *_KEY variable reaches it. Also covered: a missing transport gives 400, and sse create + connect plus streamable-http create still work.

Still open

  • The /mcp-servers routes are still unauthenticated for sse/streamable-http rows, so a caller can point the service at internal URLs (SSRF).
  • prism-service reads the same collection. Whatever it does with a stdio row is outside this guard, which covers only lazy-agent-service.
  • CORS is unchanged here (handled separately).

How it works

The shards in tool_schemas/<owner_app>/*.json are the source of truth. Only one command turns them into the flat file:

python3 scripts/export_tool_schemas.py                 # this repo's tool_schemas.json
python3 scripts/export_tool_schemas.py --check         # exit 1 if stale
python3 scripts/export_tool_schemas.py --out PATH      # another repo's copy
python3 scripts/export_tool_schemas.py --supports-out  # exit 0 on this version

Unknown arguments are an error. The old exporter read only --check and ignored everything else: run with --out or --supports-out, it rewrote this repo's file, wrote nothing for the caller, and exited 0. So running the exporter proves nothing about its version. The trading PRE_BUILD steps (and trading-service's update_tool_schemas.py) grep its source for --supports-out instead, and stop if the flag is missing.

Every copy is byte-identical because one script writes them (checked with cmp on 2026-10-22). trading-service's tests/unit/test_schema_build_publication.py pins the atomic publish and the removal of retired tools, and ToolSchemaExport.test.ts checks this repo's copy against the shards.

Editing a tool schema

  1. Edit the shard under tool_schemas/<owner_app>/.
  2. Run python3 scripts/export_tool_schemas.py and commit both files.
  3. Regenerate the trading copies with --out (their deploys also do this) and commit them in those repos.
